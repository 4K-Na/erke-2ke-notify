# 一、P0 问题

## P0-1 `t_activity` 没有陈旧回收：3 条活动永久卡在 `open`

### 问题描述

`collector_mysql.py` 只会对**上游本轮返回的活动**做 UPSERT。一旦某个活动从 `2ke` 的 `primary`/`ended` 两个列表里同时消失，它在库里就再也不会被更新——`act_state` 永远停在最后一次写入的值，`last_seen` 永远停在最后一次见到它的时间。代码里**没有任何** `gone` / 超期 / `last_seen` 过期回收逻辑（对比 jwxt 采集器有，见 P0-2）。

### 证据

上游 vs 库内逐 ID 比对（只读脚本，`Client.from_cookie_file()` + `snapshot()`，未落盘 cookie）：

```

上游 open=32 ended=200 signed_up=0  fetched_at=2026-10-28T20:02:21
库内 total=233 open=37 ended=196

--- 上游有、库里没有（漏采）：0 ---
--- 库里有、上游两个列表都没有（陈旧行）：3 ---
    cmvi0jiri00nm94n1fqmoir20 db_state=open last_seen=2026-10-27 20:42:49
    cmvp7fn870e1x94n1dn259acn db_state=open last_seen=2026-10-27 20:42:49
    cmvq7ajoi0gfl94n1g2xhmzqx db_state=open last_seen=2026-10-27 20:42:49
```

这 3 行的活动事实（`SELECT ... WHERE act_state='open' AND end_at<NOW()`）：

```
activity_id                   title                    end_at               hrs_past  last_seen            hrs_stale
cmvq7ajoi0gfl94n1g2xhmzqx     美院消防疏散演练            2026-10-28 16:00:00  4         2026-10-27 20:42:49  23
cmvp7fn870e1x94n1dn259acn     10.28消防安全讲座           2026-10-28 17:00:00  3         2026-10-27 20:42:49  23
```

- 前两条：活动**已经结束 3–4 小时**，库里仍是 `open`。
- 第三条：活动在明天，但已从上游 `primary` 消失（报名窗口关闭/被下架），`act_state` 仍是 `open`，等于告诉学生"还能报"。

总数也能对上，说明这不是偶发：

```
DB open 37 = 上游 open 32 + 陈旧 3 + 本轮 20:00 刚过期 2（cmvdzbmkw / cmvo1b6rr，end_at=20:00:00，采集发生在 19:59:13）
```

`23 小时`这个数字是关键：`last_seen` 最后一次刷新是 `10-27 20:42:49`，之后 1221 轮采集没有一轮再见过它们——即"消失"发生在 10-27 20:42，此后一直无人纠正。

### 影响

1. **后台/前台展示错误**：`act_state='open'` 的活动会被当作"开放中"。目前 `t_activity` open=37 vs 上游真实可报名 32，虚高 5 条（其中 3 条是陈旧行）。
2. **不会误推**：`dispatcher` 按 `first_seen > 水位` 增量推送，陈旧行 `first_seen` 早已过去，不会重推。所以这是**展示层数据错误，不是推送事故**——这也是它一直没被发现的原因。
3. **会继续恶化**：见下面的 200 条现象。

### 放大器证据：`ended` 列表实测恰好 200 条

```
ended 是否恰好 200 条（可能是平台硬截断）: True 200
```

而且今天一整天的采集日志显示 `ended` 是单调涨到 200 的：

```

[17:05:12] ok ... open=38 ended=194
[17:30:19] ok ... open=36 ended=196

```

`2ke` 的 RSC 载荷里没有任何 `totalRows`/`pageSize`/`hasMore` 字段（实测 `totalRows 0 次 / pageSize 0 次 / hasMore 0 次`），所以**无法从载荷判断是否有硬上限**；但"精确停在 200"+"一天内从 191 单调涨到 200"两条叠加，高度疑似列表被截断。一旦 `ended` 开始"挤出"最老的记录，凡是**在 `open` 期间被挤出**的活动就永远得不到修正——正好是现在这 3 家的成因。

### 建议修法（不动手，只给方案）

文件：`/opt/2ke-hub/collector_mysql.py`

1. 在 `collect_once()` 的 `c.commit()`（第 212 行）**之前**，加一条"本轮没见到就降级"的收尾语句，与 jwxt 采集器的做法对齐：

   ```python
   # 放在 for state, arr in (...) 循环之后、c.commit() 之前
   with c.cursor() as cur:
       cur.execute("""UPDATE t_activity SET act_state='ended'
                      WHERE act_state='open' AND end_at IS NOT NULL AND end_at < NOW()""")
       cur.execute("""UPDATE t_activity SET act_state='gone'
                      WHERE act_state='open' AND last_seen < DATE_SUB(NOW(), INTERVAL 36 HOUR)""")
   ```
   > 36 小时是保守值（一个采集周期 8 分钟，正常活动每轮都会刷新 `last_seen`）；用 `last_seen` 判断比用 `end_at` 更严谨，因为它能覆盖"活动没到结束时间但被平台下架"的情况。

2. `act_state` 字段的 `varchar(20)` 够用，但注释需同步（现在是 `COMMENT '状态 open/ended'`，实际将有 `gone`）：
   ```sql
   ALTER TABLE t_activity MODIFY act_state varchar(20) DEFAULT 'open' COMMENT '状态 open/ended/gone'  -- 仅建议，本次未执行
   ```

3. 顺带补一条"本轮条数"监控：把 `n_open + n_ended` 与上一轮对比，变化超过 ±10% 时打 WARNING（现在只有 `ok ... open=%d ended=%d` 的事实日志，没有任何基线对比）。

## P0-2 jwxt 采集器没有分页，却用"本轮没返回就标 `gone`"做全量收敛

### 问题描述

`collector_jwxt.py` 请求 `/un-enroll-search` 时**不带任何分页参数**（`fetch("/un-enroll-search", cookie)`，第 493 行），而服务端默认分页。随后第 561–567 行做了这件事：

```python
live_ids = [int(r["id"]) for r in rows if r.get("id")]
if live_ids:
    fmt = ",".join(["%s"] * len(live_ids))
    with c.cursor() as cur2:
        # 官网已下架但库里还是 open 的
        cur2.execute("UPDATE t_lecture SET act_state='gone'"
                     " WHERE act_state='open' AND lecture_id NOT IN (" + fmt + ")", live_ids)
```

**`NOT IN` 的补集 = 整个库里所有不在第一页的讲座。** 只要第一页装不下全部讲座，第 21 条起会被全部标成 `gone`，而且每轮都会重复标。

### 证据

实测上游信封（只读 GET，用现有 `cookie.txt`）：

```
信封 keys: ['_page_', '_sorts_', 'data']
_page_ = {'currentPage': 1, 'rowsInPage': 2, 'rowsPerPage': 20, 'totalPages': 1, 'totalRows': 2}
```

- `rowsPerPage: 20` —— **服务端默认每页 20 条**，请求里没有覆盖它。
- `currentPage: 1`、`totalPages` 字段存在 → 接口明确支持分页，采集器完全没用。

代码侧确认没有分页参数（grep 全文只有一处 `fetch(` 调用）：

```
493:    data, st1 = fetch("/un-enroll-search", cookie)
```

而拿到 `_page_` 之后只是打印，**不做任何校验或告警**：

```
511:    page = data.get("_page_") or {}
512:    log("接口返回 %d 条（totalRows=%s）" % (len(rows), page.get("totalRows")))
```

当前只有 2 条讲座（`totalRows=2`，`totalPages=1`），所以还没爆。这是**时间问题，不是概率问题**：讲座数 >20 的那一周 100% 触发。

### 影响

1. 第 21 条起所有讲座在库里变 `gone`，`last_seen` 停止刷新 → 后台"讲座列表"大面积显示为已下架/消失。
2. **静默**：日志只会多一行 `接口返回 20 条（totalRows=35）`，没人会去看这个差值；`state.json` 仍然是 `ok: true`。
3. 与 P0-1 是同一类病（"平台没返回" ≠ "平台没有了"），但 jwxt 这边因为 `NOT IN` 全量标记，破坏面大得多。

### 建议修法

文件：`/opt/jwxt/collector_jwxt.py`

1. 第 493 行改成翻页取全量（`rowsPerPage` 服务端接受覆盖，若不被接受则按每页 20 递增 `page`/`currentPage` 直到取满 `totalPages`）：

   ```python
   rows, seen = [], 0
   for p in range(1, 51):                      # 硬上限 50 页，防死循环
       data, st1 = fetch("/un-enroll-search?page=%d&rowsPerPage=100" % p, cookie)
       if data is None: ...                    # 沿用现有失败分支
       pg = data.get("_page_") or {}
       rows.extend(data.get("data") or [])
       if pg.get("currentPage", 1) >= pg.get("totalPages", 1): break
   ```

2. 加一条硬断言（比什么都重要）：

   ```python
   total = int((data.get("_page_") or {}).get("totalRows") or 0)
   if total and len(rows) < total:
       log("!! 分页未取全：拿到 %d / totalRows=%d，本轮不标 gone" % (len(rows), total))
       # 本轮跳过 gone 收敛，避免误标
       return 4
   ```

3. `NOT IN` 全量标记本身建议加"只对本轮之前就已存在、且本轮 last_seen 未刷新的行"限定，减小爆炸半径：
   ```sql
   UPDATE t_lecture SET act_state='gone'
    WHERE act_state='open' AND last_seen < %s AND lecture_id NOT IN (...)
   ```
   （`last_seen < 本轮开始时间`，即可，避免把本轮刚 upsert 的行也扫进去。）

## P1-2 jwxt 告警把"任何取数失败"都报成"TGC 自动续期已失效"

**证据**（`collector_jwxt.py` 第 493–508 行）：`fetch()` 返回 None 的所有情形（`HTTP 502`、`HTTP 500`、超时、非 JSON）都会走到同一段告警，正文写死：

```python
msg = ("【集大教务·讲座采集】登录态失效\n\n"
       "原因：%s\n\n"
       "TGC 自动续期已失效，需要你重新登录一次：\n" ...)
```

而 `fetch()` 的错误分类里本来就包含 `"HTTP %s"`（第 94 行）和 `"ERR %r"`（第 96 行）。

**影响**：教务站点一次 502 或网络抖动，管理员会收到"TGC 已失效，请重新登录"的错误指引，白折腾一次取 TGC。且冷却 1 小时（`ALERT_COOLDOWN=3600`）内后续真正的失效告警会被压掉。

**建议**：按 `st1` 前缀分流——`st1.startswith("HTTP") or st1.startswith("ERR")` 走"上游/网络异常"文案（不含换 cookie 步骤），只有 `"非 JSON"` 才走"登录态失效"文案。

## P1-3 TGC 续期机制的三个脆弱点

**证据 1（TGC 从不轮换，但代码也不保存轮换值）**：

```
/opt/jwxt/tgc.txt  600 root:root 111 bytes mtime=2026-10-28 18:06:32
/opt/jwxt/cookie.txt 600 root:root 90 bytes mtime=2026-10-28 20:00:27
```

`tgc.txt` 自 18:06 之后再没变过，而 18:23 / 18:30 / 18:53 / 19:00 / 19:30 / 19:49 / 20:00 **连续 8 次** `TGC 续期成功`。说明 CAS 目前不轮换 TGC。但代码把 TGC 塞进 `http.cookiejar`（第 166–172 行）后，**从不回读 jar 里的新 TGC、也从不写回 `tgc.txt`**。哪天 CAS 开始轮换（这是 CAS 的标准行为），旧 TGC 立即失效，而脚本里还是旧的。

**证据 2（`tgc_ok` 没有历史）**：

```
cat /opt/jwxt/state.json
{
 "ok": true, "last_error": "", "last_ok": "2026-10-28 20:00:27",
 "total_rows": 2, "new": 0, "updated": 2,
 "tgc_ok": true, "pushed": 0, "baseline_done": true
}
```

只有"当前值"，没有时间序列。`tgc_dead_at` 字段只在失败时写入、成功时 `pop` 掉。所以**没法回答"过去 N 天有没有失效过、失效了多久"**——这个问题的历史答案是"不可考"。

**影响**：判断"还能撑多久"只能靠外部知识（CAS TGC 通常有数天到数周的空闲超时），服务器侧无任何可观测数据。

**建议**：
1. `refresh_session_from_tgc()` 结束后回读 jar 里的 `TGC`，与 `tgc.txt` 不同则原子写回（复用 `save_state` 的 `.tmp + os.replace + 0600` 套路）。
2. `state.json` 加 `tgc_ok_since`（本次连续成功起始时间）与 `tgc_fail_count`，失败时不覆盖成功时间，形成最小可观测历史。

## P1-5 `act_state` 有两个写入者，规则不同且无状态守卫

**证据**：除采集器外，**后端也在写这一列**。

```
/opt/ruoyi/ruoyi-system/src/main/java/com/ruoyi/system/mapper/TLectureMapper.java:57:    int closeExpired();
/opt/ruoyi/ruoyi-system/src/main/java/com/ruoyi/system/controller/TLectureController.java:113:                lectureMapper.closeExpired();
```

`closeExpired()` 的实现（同文件第 55 行附近）：

```java
@Update("UPDATE t_lecture SET act_state = 'ended' WHERE open_end IS NOT NULL AND open_end < NOW()")
```

这条没有 `AND act_state IN ('open','gone')` 守卫，会把采集器刚标的 `gone` 直接改写成 `ended`。而采集器的收敛语句（`collector_jwxt.py:570-571`）是有守卫的。

**影响**：同一列的最终值取决于"先谁后谁"。目前无害（讲座结束后 `ended` 确实比 `gone` 更准确），但一旦将来有人给 `gone` 加上不同语义（例如"取消"), 就会互相打架。

**建议**：统一到一个写入者。最省事的做法是删掉 `closeExpired()` 的调用点（采集器 30 分钟一轮已经覆盖过期收敛），或给它补上 `AND act_state IN ('open','gone')` 与采集器保持完全一致的谓词。

```python
        log("  !! 推送异常 %r" % (e,))     # ← 只写日志，不告警、不重试、不落库
```

而 `push_new_lectures()` 只在**发现新讲座的那一轮**被调用（`new_list` 来自 `rowcount==1`）。如果它在第 5 个订阅者处抛异常：前 4 个人收到、写入了投递记录；后 15 个人没收到、没有记录；**下一轮 `new_list` 为空，永远不会补**。`retry_failed_lectures()` 只捞 `send_status='failed'` 的行，而这 15 个人连行都没有。

**影响**：静默漏推。日志里只有一行 `!! 推送异常`，没有企业微信告警。

**建议**：把 `push_new_lectures()` 内部改成"逐条 `try` + 失败的写 `failed` 记录"，外层 `except` 里补 `send_alert()`；并把 `new_list` 的非空判断换成"存在 `send_status IS NULL` 的（lecture_id × subscriber）组合"来兜底补发。

## P1-8 2ke 采集器失败不自己告警，只靠 dispatcher 的 40 分钟巡检

**证据**：`collector_mysql.py` 的失败分支只 `print`（第 244–250 行），没有任何推送通道。真正的告警在 `dispatcher.py`：

```
565:STALE_MINUTES = 40          # 采集器 40 分钟没更新数据就认为它死了
615:        cur.execute("SELECT MAX(last_seen) AS last, COUNT(*) AS n FROM t_activity")
624:    if idle <= STALE_MINUTES: ... return
```

**影响**：
1. 失效检测延迟 ≥40 分钟（`SESSION_EXPIRED` 分支还先退避 1800s，所以最坏情况 40 分钟后才有一条"已 N 分钟没采集到数据"）。
2. **告警能力依赖 dispatcher 自己活着**——两个服务同机同库，dispatcher 挂了则采集故障彻底无声。
3. 巡检判据是 `MAX(last_seen)`，只能发现"整体停摆"，**发现不了 P0-1 那种"个别行陈旧"**（那 3 行 `last_seen` 停 23 小时，`MAX(last_seen)` 依然是 20:00:27，巡检认为一切正常）。

**建议**：`collector_mysql.py` 在 `fail` 连续 ≥2 次时自己发一条企业微信（可复用 `wecom.json` 与 jwxt 的 `send_alert` 冷却套路）；巡检增加第二条判据——`SELECT COUNT(*) FROM t_activity WHERE act_state='open' AND last_seen < NOW()-INTERVAL 6 HOUR`。

## P1-9 "`new=0` 但上游真的变了"没有任何断言

**证据**：两个采集器的成功判据都只看"这轮有没有抛异常"，不比对"上游总量是否变化"。

- 2ke：`assert_payload()` 只挡三种情况（缺 `primary`/`ended` key、`open+ended==0`、引用块形态），**不校验条数**。载荷里也没有 `totalRows` 可用（实测 0 次命中），所以条数断言只能靠"与上一轮比"。
- jwxt：`totalRows` 明明拿到了（`collector_jwxt.py:512`），但只打印不判断。

**影响**：平台侧列表被截断/过滤（如 P0-1 的 200 上限、cookie 对应的账号失去某些可见范围）时，采集器会稳定输出 `ok ... new=0`，看起来完全健康。

**建议**：把 `open+ended`（2ke）/ `totalRows`（jwxt）写入 `state.json`，与上一轮比较；单轮变化超过 ±10% 且绝对值 >5 时打 WARNING 并发告警。
