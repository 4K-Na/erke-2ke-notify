### P0-2 讲座推送是"先发后记"，没有真正的幂等闸门（同一讲座可被反复全量重发）

**描述**
二课侧的做法是「先 `INSERT ... pending`，只有 `affected_rows==1` 才发」（`dispatcher.py:923-940`），所以并发、重跑、手滑都不会双发。讲座侧相反：

```python
# collector_jwxt.py:367-379
for r in new_rows:
    content = render_lecture_rich(r)
    for sb in subs:
        ok, err = wecom_send_text(tok, agent, ext, content)   # ← 先发
        _record_delivery(c, r["id"], ..., "sent" if ok else "failed", ...)  # ← 后记（ON DUP 覆盖）
```

`_record_delivery()`（`385-395`）是 `INSERT ... ON DUPLICATE KEY UPDATE send_status=VALUES(...)`，**不判断是否已存在**：只要有人用同样的 `new_rows` 再调一次 `push_new_lectures`，消息就会**再发一遍**，然后把已有记录再改一次。唯一的"幂等"来自调用方：`new_list` 只在 `upsert()` 返回 `rowcount==1` 时才有内容（`collector_jwxt.py:553`）。

**证据**

1. 代码如上（`collector_jwxt.py:367-395`）。
2. 幂等基石 `UNIQUE(lecture_id, subscriber_id)` 的 `subscriber_id` **可为 NULL**（`SHOW CREATE TABLE t_lecture_delivery`：`subscriber_id bigint(20) DEFAULT NULL`），baseline 登记行正是 `NULL`，MySQL 唯一索引对 NULL 不去重——**baseline 行对这些讲座的真实发送没有任何约束力**，每次调用还会再插一条新的 NULL 行。
3. P0-1 就是这条缺口的现实版：`send_lecture_all.py` 只加了一层"查一遍 `send_status='sent'` 就跳过"的临时判断，换个脚本、或者传一个 `skipped` 行进来，立刻就是全量重发。

**影响**
只要再有一次"重跑采集器 / 手工补发 / 表重建或恢复备份 / 给脚本改个参数"，19 名学生就会再收一遍同样的讲座消息。二课侧有唯一键 + pending 双保险，讲座侧只有单层且可被绕过。

**建议**
讲座侧照抄二课的三层：① 发送前 `INSERT ... pending`（唯一键冲突就跳过，不发）；② 只有 `affected_rows==1` 才 `wecom_send_text`；③ 发送结果回写同一行。`subscriber_id` 设 `NOT NULL`（baseline 用一个专门的 `subscriber_id=0` 或独立列 `kind='baseline'`），否则 NULL 行永远不受唯一键约束。

### P1-1 两条推送链路对同一批人是"零协调"，实测已出现 20 秒 3 连推

**描述**
活动推送（`2ke-dispatcher`，120s 一轮）和讲座推送（`jwxt-collector.timer`，每 30 分钟，:00/:30 准点）**各自独立、都向 `t_subscriber.status='0'` 的同一批 19 人发送**，两者之间没有任何互斥、节流、合并或时间窗：

- 没有静默时段（用户要求删除，`dispatcher.py` 里 `in_quiet_hours()` 已成死代码 → 见 P2-1），所以**凌晨 00:00–06:00 发现新讲座/新活动照样立即全量推送**
- 讲座推送**一场讲座一条消息**，不做合并：实测 `19:44:59 → 19:45:19` 的 20 秒里连发 3 条，学生手机连响 3 次
- 讲座 timer 是 `OnCalendar=*:0/30`，activity dispatcher 每 120s 扫一次，两者在同一分钟内撞车的概率不低
- 两条链路的过滤规则完全不同（见 P1-2），学生无法预期"我到底会收到什么"

**证据**

1. `systemctl cat jwxt-collector.timer` → `OnCalendar=*:0/30`；`2ke-dispatcher` → `INTERVAL=120 / SYNC_INTERVAL=60`（`dispatcher.py:59-61`）。
2. 同一天实测：`17:05:39` 活动推送 19 条（`t_delivery` 最近一批，活动"10.31音乐2612草坪音乐会"）+ `19:44:59–19:45:19` 讲座推送 57 条 → 19 人在 2.5 小时内收到 4 条消息，其中 3 条在 20 秒内。
3. 两条链路的接收者集合完全相同：`dispatcher.py:795-798` `SELECT ... FROM t_subscriber WHERE status='0'`；`collector_jwxt.py:361-364` `SELECT ... FROM t_subscriber WHERE status='0' AND channel='wecom'`。当前 `t_subscriber`：`status=0` 共 19 人。
4. 全库 `t_delivery` 无一条夜间发送记录只是"恰好晚上没新活动/新讲座"，代码里没有任何时间窗判断（grep `in_quiet_hours` 只有定义，无调用）。

**影响**
订阅者数一旦上三位数、讲座进入密集期（每学期开学),学生会同时收到"第二课堂：有新活动!"和"讲座：有新讲座"两套格式、两个链接体系的消息，骚扰感成倍放大，退订风险上升。

**建议（不改代码也能先做）**
1. 讲座 timer 改成白天窗口跑（`OnCalendar=*:0/30` → 加 `08:00–22:00` 的时间范围），至少先消除凌晨轰炸。
2. 讲座推送改成"一轮合并一条"（"今晚有 3 场新讲座：…"）——这是文案层改动，可先在采集器里拼一条多条正文再发一次。
3. 给两条链路加一个共享的"今日已推送条数/最后推送时间"文件（`/opt/2ke-hub/last_push.json`），任一条链路发送前检查"距上次 < 60s 就等下一轮"。

### P1-2 讲座推送完全绕过订阅者的过滤规则，也不看讲座状态

**描述**
`push_new_lectures()` 取订阅者时只筛 `status='0' AND channel='wecom'`，**完全不看 `keywords` / `only_school` / `min_credit`**——学生在后台设的"过滤规则"对讲座消息 100% 无效。二课侧 `match()`（`dispatcher.py:369-395`）会逐条判断这三项。同时 `new_list` 里包含所有新入库讲座，**不筛 `act_state`**，所以一门刚被采集到、但 `open_end` 已经过去的讲座也会立即推给所有人（二课侧有 `AND act_state='open'`）。

**证据**

1. `collector_jwxt.py:361-364`（订阅者查询无过滤条件）；`:367` 直接 `for r in new_rows` 无状态判断，`:550` 才计算 `act_state`。
2. 后台订阅者页"过滤规则"列实测全部显示"全部活动"（`t_subscriber` 19 行 `keywords=NULL, only_school='0', min_credit=NULL`）——**现在恰好没有差异，但功能是断的**：任何一个学生设了"只看志愿"，讲座消息照收。
3. 对比 `dispatcher.py:372-394`：`status` / `keywords` / `only_school` / `min_credit` 四项齐全。

**影响**
过滤功能对讲座失效（功能承诺与实际行为不符）；一旦讲座出现"已结束/已下架"仍会被推（P0-1 里 8546 就是报名截止后才发的）。

**建议**
讲座推送复用同一套过滤：把 `match()` 抽成公共模块（或复制一份），并在 `new_rows` 上加 `act_state='open' AND (enroll_end IS NULL OR enroll_end > NOW())` 条件。

### P1-3 讲座侧重试"口径与二课一致"这句是错的：缺 unknown 三态，超时会被当失败重发

**描述**
`collector_jwxt.py` 的文档与 `SYSTEM-档案.md` §9.4 都写"失败重试口径同二课：'unknown' 类不重发（可能已送达）"，但代码里根本没有 unknown：

```python
# collector_jwxt.py:288-300
try:
    r = json.load(urllib.request.urlopen(req, timeout=20))
    return r.get("errcode") == 0, r.get("errmsg", "")
except Exception as e:
    return False, repr(e)          # ← 超时/连接重置/HTTP 5xx 全部落这里 → 写成 failed
```

`retry_failed_lectures()`（`:398-458`）随后只捞 `send_status='failed'` 且 `attempt<3` 且 6 小时内的行重发 → **一次 20 秒超时（消息其实已送达）就会导致学生收到两遍同样的讲座**。二课侧对同一场景的处理是 `UNKNOWN=-1` + `attempt=99` 直接移出重试队列（`dispatcher.py:968-979`）。

**证据**

1. 代码如上（`collector_jwxt.py:288-300`、`398-411`）。
2. 二课侧对照：`dispatcher.py:147-193`（三态语义注释）+ `:968-979`（`unknown` 且 `attempt=99`）。
3. 好消息：当前 `t_lecture_delivery` 无 `failed` 行，这个 bug 还没被触发过。

**影响**
重试即可能重复推送（正是用户最反感的"收两遍"）。文档与代码不一致会让下次接手的人误判。

**建议**
`wecom_send_text()` 改成返回 (ok, errcode, errmsg) 三态，超时/连接异常返回 `UNKNOWN` 并写 `send_status='unknown' + attempt=99`；`retry_failed_lectures()` 只捞 `failed`。

### P1-4 讲座名额口径可疑：`enrollCount` 三场全部恰好等于 `upperLimit`

**描述**
推送文案会写「名额：174 人（已报 174，剩 0）」。但 `t_lecture` 现有 3 行里，`enroll_count` 与 `upper_limit` **完全相等**（150/150、330/330、174/174），而 `report_count`（已签到）分别是 0、0、112。3/3 全部"恰好满额"在统计上极不正常，怀疑 `/un-enroll-search` 返回的 `enrollCount` 并不是"已报名人数"（可能是 upperLimit 回填或"剩余名额"语义）。

**证据**

1. `SELECT lecture_id, upper_limit, enroll_count, report_count, ... FROM t_lecture`：
```
| 8485 | 数智赋能讲座系列：脑与生活      | 150 | 150 |   0 |
| 8531 | 与压力同行——大学生压力识别…    | 330 | 330 |   0 |
| 8546 | 从地震到海啸                    | 174 | 174 | 112 |
```
2. `raw_json` 原始字段同样是 `enrollCount=150 / reportCount=0 / upperLimit=150`，即不是入库转换的问题。
3. 渲染实测输出（真实数据）：
```

```

**影响**

**建议**

### P1-5 公告管理权限标识三处不一致（非超管角色一定出问题）

**描述**
同一个"公告管理"功能，菜单、页面、接口用了三套权限字符串：

| 位置 | 权限标识 |
|---|---|
| `sys_menu` 2021「公告管理」 | `system:tnotice:list` |
| `TNoticeController` 全部接口（`list/add/edit/remove/export/getInfo`） | `system:notice:*` |
| `views/system/tnotice/index.vue` 顶部按钮（32/42/52/61 行） | `system:notice:*` |
| `views/system/tnotice/index.vue` 行内按钮（104/105 行） | `system:tnotice:edit` / `system:tnotice:remove` ← **`sys_menu` 里不存在** |

`admin` 是超管（`*:*:*`）所以一切正常；但任何非超管角色勾选"公告管理"后，只能拿到 `system:tnotice:list`，打开页面调 `/system/tnotice/list` 会因缺 `system:notice:list` 被拒；即使补了这个权限，行内的"修改/删除"按钮因 `system:tnotice:edit/remove` 在菜单表里根本不存在而**永远不显示**。

**证据**

1. `sys_menu`：`2021 | 公告管理 | parent=0 | order=5 | path=tnotice | perms=system:tnotice:list`，且 **2021 下没有任何 `F` 型按钮**（公告的新增/修改/删除/导出按钮权限 `1035–1038` 挂在 107「通知公告」下面，而 107 属于 `visible=1` 隐藏的「系统管理」）。
2. `TNoticeController.java:41/53/66/76/87/98` 全部 `@PreAuthorize("@ss.hasPermi('system:notice:...')")`。
3. `views/system/tnotice/index.vue:32,42,52,61` 用 `system:notice:*`；`:104,105` 用 `system:tnotice:edit/remove`。
4. 全库 `sys_menu` 里 `perms LIKE 'system:tnotice:%'` 只有 `system:tnotice:list` 一条（`grep` 结果），`system:tnotice:edit` / `system:tnotice:remove` 不存在。

**影响**
新增管理员/助管角色时，公告管理要么进不去（403），要么按钮消失；现在只有 admin 一个人用，所以没暴露。

**建议**
统一成一套（推荐全部改成 `system:tnotice:*`，因为表是 `t_notice`，而且 `system:notice:*` 已被原生的「通知公告」占用，容易串），并在 2021 下补 5 个按钮菜单（查询/新增/修改/删除/导出）。

### P1-7 采集进程无互斥，"立即采集"与 timer 可并发，重试会双发

**描述**
后台「立即采集」直接在 Tomcat 线程里 `new ProcessBuilder(...).start()` 跑 `collector_jwxt.py`（`TLectureController.java:94`），**与 `jwxt-collector.timer` 没有任何锁**。两个实例同时跑时：
- 新讲座入库有唯一键，不会被重复推送（安全）
- 但 `retry_failed_lectures()` 的读—发—写没有行锁，两个进程会同时捞到同一批 `failed` 行、各发一次 → **重复推送**

二课侧同理：`dispatcher.py --once` 与常驻进程并发时，`retry_failed()`（`:668-682` 先 SELECT 再逐条发）也没有保护。

**证据**
1. `TLectureController.java:94-97`（`pb.start()`，无 flock、无 pid 文件）。
2. `systemctl cat jwxt-collector.timer` → `OnCalendar=*:0/30`，与人工点"立即采集"完全可能撞在同一秒。
3. `collector_jwxt.py:398-458` / `dispatcher.py:657-718`：都是 `SELECT failed` → `send` → `UPDATE`，中间无 `SELECT ... FOR UPDATE`、无状态抢占。

**影响**
现在 `failed` 行是 0，所以没发生；一旦企业微信抖动产生 failed 行，重试就可能双发。

**建议**
采集入口加文件锁（`flock /var/lock/jwxt-collector.lock`）—— 后台改成 `systemctl start jwxt-collector.service` 调用同一个 oneshot 单元最省事，由 systemd 天然互斥；重试改成先 `UPDATE ... SET attempt=attempt+1 WHERE delivery_id=? AND send_status='failed'` 抢占，`affected_rows==1` 才发。

### P1-8 手动推送"文图分开发"不是原子的，失败提示还会误导

**描述**
`TPushController.send()` 先发文字（`:126`），再发图片（`:148-149`）。两种坏情况处理都不理想：

1. **文字失败但图片照发**：`textOk=false` 时不会 `return`，仍继续走图片分支（`:132-157`），学生收到一张没有上下文的图；接口返回 `"文字发送失败：…"`，管理员不知道图已经发出去了。
2. **文字成功、图片失败**：返回 `AjaxResult.error("文字已发出，但图片失败：…")`；前端 `request` 拦截器对 `code!==200` 统一走 `catch`（`utils/request.js:99-106`），页面「上次发送结果」卡片被写成 `ok:false / errcode:'-'`（`views/system/push/index.vue:226-234`），**看不出"文字那半条已经成功"**，管理员很可能再点一次 → 文字重复发送。
3. 结果卡片的字段与后端返回结构不匹配：后端返回 `{text:{ok,errcode,errmsg}, image:{...}, withImage}`，前端读的却是顶层 `d.errcode / d.touser / d.msgid`（`:220-223`），所以"errcode"永远显示 0、"接收人"显示的是 `self/all/ids` 这样的 scope 枚举值。
4. 图片失败后**没有任何重试或补发入口**，也不写 `t_delivery`（`TPushController` 注释明确说手动消息不入投递表），事后无法确认谁收到了文字、谁没收到图。

**证据**
1. `TPushController.java:125-157`（顺序 + 不短路 + 部分成功返回 error）。
2. `views/system/push/index.vue:211-234`（成功分支只处理 HTTP 200；catch 分支不读后端 data）。
3. `utils/request.js:99-106`（`code===500` → `ElMessage.error` + `reject(new Error(msg))`）。
4. 实测页面结构正常（`shots/push_index.png`，"勾了图片就分两条发——先发文字，紧接着发图片"提示存在），说明这是"实现层"而非"文案层"问题。

**影响**
一次"文字成功 + 图片失败"就会让管理员误判整条失败并重发 → 学生收到两遍文字。@all 场景下影响 19 人。

**建议**
- 文字失败就立即 `return error`，不发图片（或用 `if (textOk && imgRes != null)` 包住图片段）
- 部分成功返回 `code:200` + `data` 里带 `textOk/imageOk`，由前端用不同颜色展示"文字✅图片❌"，并在卡片上显示后端返回的 `errmsg`
- 给图片失败留一个"只重发图片"的入口（同一次 media_id 3 天内有效）

### P1-9 二课文案把内部运维话术推给学生，并违反"不许用 2ke 简称"的硬约束

**描述**
`dispatcher.render()` 在"报名开始晚于活动结束"时，直接把 `报名：平台数据异常（晚于活动结束），以 2ke 为准` 写进发给学生的消息（`dispatcher.py:519-521`）。这句话有两个问题：① 硬约束 §7-3 明确「不要用『2ke』简称，一律写『第二课堂』」，而这是**对外推送正文**；② "平台数据异常…以…为准" 是给运维看的判断，学生看不懂，也不知道"那我到底能不能报"。

**证据**
1. 代码 `dispatcher.py:518-521`。
2. 真实数据渲染输出（用 `render()` 跑库里的真实记录）：
```
【机械学院团干培训】
学分：最高 0.2 学分
时间：2026-11-08 00:00 ~ 2026-11-08 23:59
报名：平台数据异常（晚于活动结束），以 2ke 为准
```
3. 命中该分支的 `act_state='open'` 活动：**2 条**（`cmvq679590gao94n1l7d2x1uz`、`cmuy9p4n101gvu3teujmgpxyg`），只要它们是"新发现的"就会原样推给 19 人。
4. 同类问题：`signin_end` 已过期的 open 活动 **7 条**，代码没有任何"已截止就不推"的判断（`dispatcher.py:517-526` 只做"晚于结束"的兜底，不做"已过期"判断）；`quota IS NULL` 的 1 条会输出"名额：不限"，容易被读成"名额无限"。

**影响**
学生收到看不懂的话术 + 违反用户明确定的文案规范；已截止活动的推送会让学生白点一次。

**建议**
改成学生能理解的中性表述，例如 `报名：时间待活动方确认，请进平台看详情`（去掉"2ke"和"异常"）；对 `signin_end < now()` 的活动加一条 `act_state='open' AND signin_end >= NOW()` 的推送判定（或至少在文案里标"报名已截止"）。
